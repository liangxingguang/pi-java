# 写作规则：技术记录、工单、裁决文档生成规范
适用范围：任务描述、架构裁决、风险记录、迭代说明、工单正文、评审纪要。
目标：避免生成高度压缩、黑话堆砌、长嵌套复合句的文本；产出内容必须能让本项目开发/测试读懂。

## 1. 上下文前置要求
1. 文档开头必须放【背景摘要】，一句话说明本段记录对应的迭代/事件。
2. 项目专有名词**第一次出现附带简短释义**；同文档后续可直接简写。
   项目固定术语词典（内置）：
    - Bxxx：工单编号
    - 模型可见面：大模型能够读到的输出文本、报错文案；内部代码逻辑属于【模型不可见】
    - 逐字化 / 逐字可钉：文本严格对齐PI契约，文字固定不可随意改动
    - 窄差表：记录Java实现与PI契约无法完全对齐的差异清单，D2/D5为表内条目，§5.4为文档章节
    - telemetry：埋点
    - 裁决(ruling)：架构/实现取舍决策，附带风险评估
3. 区分两类文档形态，根据输出目标选择：
    - 【架构备忘录】：允许简写、内部代号、紧凑句子、章节引用；用于架构师之间记录决策。
    - 【开发工单】：人话优先、分点、术语释义、清晰风险；给开发、测试执行，**本规则默认优先输出工单版**。

## 2. 句子与段落硬性约束
1. 一句话只描述**一件事情**。禁止单句同时混杂：现状问题 + 代码实现 + 副作用代价 + 文档章节引用。
2. 禁止超长嵌套破折号、多层分号串联长句。长段落必须拆为列表。
3. 单条裁决统一固定三段式模板（工单版强制使用）：
> 【场景】：描述原始问题/冲突
> 【决定】：选择的实现方案
> 【风险/代价】：改动带来的副作用、边界场景；标记 [模型可见] / [内部，模型不可见]

## 3. 裁决记录专项规则（Rulings I made）
1. 每条裁决独立列表项，不合并多条裁决到同一段落。
2. 风险区分等级：`无影响` / `边缘场景` / `[模型可见]文案差异` / `存量约束，非本批范围`。
3. 文档引用（D2/D5、§5.4、工单Bxxx）放在条目末尾，不要放在句子主干。
4. 必须明确标注：改动是否属于【模型可见面】，模型可见的契约文案优先对齐PI逐字要求。
5. 区分：
    - ✅ 模型可见：输出文案、报错提示、schema、模板行文，尽量逐字对齐PI
    - ✅ 内部引擎：Java遍历、栈逻辑、IO、线程竞态等内部代码，优先保证稳定性
    - ✅ 无法消除差异：统一登记入窄差表，不要散落在代码注释

## 4. 生成完成后，强制自检2条
输出完成，自行校验下面两条，不通过则重写：
1. 不熟悉该模块的开发，不翻阅外部文档，能否看懂「做了什么，风险是什么」。看不懂 → 补充术语释义或拆分。
2. 是否存在单段同时混杂多件事情。是 → 拆分为列表或独立小节。

## 5. 禁止行为
1. 禁止直接输出原始架构草稿文本作为开发工单。
2. 禁止裸写内部代号，首次出现不加解释。
3. 禁止把背景、方案、风险挤在同一个长复合句。
4. 禁止混用架构备忘录简写风格到开发任务工单。
